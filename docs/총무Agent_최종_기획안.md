# 총무 Agent 최종 기획안

2026년 10월 2일 · @Someone

## 한 줄 요약

사내 행사 회비(계좌이체)의 입금 대조, 마감 후 변동 반영, 단계적 독촉·환불 확인을 기록·정산·소통 세 에이전트가 나눠 맡고, 총무는 정산 리포트 한 장만 보고 송금하는 업무용 앱입니다. 팀원 제안(단계적 독촉, 입금 문자 인식, 에이전트 3분할, Slack 채널)을 반영한 버전입니다(10장).

과제 요건(Category C)과의 대응은 다음과 같습니다.

| 요건 | 이 기획에서 |
|---|---|
| 업무용 AI Agent 앱 | 사내 행사 총무의 회비 정산 업무 |
| AI Agent 반드시 적용 | 기록·정산·소통 3개 에이전트 (5장) |
| Workflow 정의 (적용 전/후 비교) | 7장 |
| 2인 공동 발표 | 역할별로 발표 파트 분담 (9장) |

## 1. 문제 정의

총무가 가장 시간을 쓰는 일은 계산이 아니라 통장 입금 내역과 명단을 한 줄씩 대조하는 일입니다.

- 상황: 기업 워크숍·연수. 숙박비·교통비는 회사 예산으로 처리하고, 참가자에게는 소정의 회비만 계좌이체로 받습니다.
- 입력하는 사람: 참가자. 마감 전까지 공유 시트에서 본인 행을 직접 수정합니다.
- 최종 사용자: 총무. 행사가 끝난 뒤 리포트만 보고 환불·추가 납부를 처리합니다.

지금 총무가 겪는 불편은 세 가지입니다.

1. 입금자명이 명단과 달라서(이름 순서, 대리 입금, 소속 표기, 동명이인) 한 줄씩 확인해야 합니다.
2. 마감 후 "버스 안 탈게요" 같은 변동이 메신저로 흩어져 들어와 표에 옮겨 적어야 합니다.
3. 환불 대상자를 찾고, 계좌를 묻고, 추가 납부자를 독촉하는 연락을 일일이 해야 합니다.

### 회비 규칙과 차액

회비는 참가 시 필수이며 버스 이용 20,000원, 미이용 15,000원 두 가지뿐입니다. 정산은 이 회비의 차액으로만 한정합니다.

마감 시점의 시트가 회비 기준이 되고, 마감 후 변동만 차액을 만듭니다.

| 마감 기준 | 최종 | 차액 | 처리 |
|---|---|---|---|
| 참가 + 버스 (20,000) | 참가 + 미이용 (15,000) | −5,000 | 환불 5,000 |
| 참가 + 미이용 (15,000) | 참가 + 버스 (20,000) | +5,000 | 추가 납부 5,000 |
| 불참 | 참가 (마감 후 추가) | +15,000 / +20,000 | 추가 납부 |
| 참가 | 불참 (마감 후 취소) | — | 제안: 환불 없음 (기록만) |

예시: 마감 기준 50명(버스 40명, 미이용 10명) = 950,000원. 마감 후 버스→자차 3명, 자차→버스 1명, 불참 2명, 신규 참가(버스) 1명이 생기면 환불 3명 15,000원, 추가 납부 2명 25,000원, 최종 회비 총액은 960,000원입니다.

계산 자체는 시트 수식으로 충분합니다. 에이전트는 계산이 아니라 대조와 연락을 맡습니다(5장).

## 2. 시스템 구성

Google Sheets 하나 + Apps Script로 만듭니다. 별도 서버 없이 시트에서 동작하고, Cursor로 스크립트를 작성할 수 있어 제출 일정에 맞습니다.

### 시트 탭

| 탭 | 편집 | 내용 |
|---|---|---|
| 참가 명단 | 참가자 (본인 행만) | 이름, 소속, 참가(O/X), 버스(O/X), 비고 |
| 정산 현황 | 에이전트 | 최종 회비, 납부액, 차액, 상태 |
| 규칙 | 총무 | 회비 금액, 마감 시각, 마감 후 불참 처리 등 |
| 입금 내역 | 총무 (거래내역 업로드 또는 입금 문자·캡처 붙여넣기) | 입금일, 입금자명, 금액 |
| 마감 스냅샷 | 스크립트만 (숨김) | 마감 시각의 명단과 회비 기준 |
| 변동 로그 | 스크립트만 (숨김) | 마감 후 변동 한 줄씩 |
| 정산 리포트 | 자동 생성 | 총무가 보는 최종 결과물 |

### 마감 전·후 처리

- 마감 전: 참가자가 참가·버스 칸을 자유롭게 수정합니다. 이전 값은 남기지 않습니다. 칸은 체크박스나 드롭다운으로만 받아 입력 실수를 막습니다.
- 마감 시각: 시간 기반 트리거가 참가·버스 열을 잠그고, 그 시점 명단을 마감 스냅샷에 저장합니다.
- 마감 후: 변동은 비고나 Slack 메시지로만 받습니다. 에이전트가 해석해 변동 로그에 기록하고 정산 현황을 갱신합니다.

### 변동 로그 열 (두 사람의 접점)

| 열 | 예시 |
|---|---|
| 변동 ID | C-007 |
| 참가자 | 김민지 (영업1팀) |
| 항목 | 버스 |
| 이전 → 이후 | O → X |
| 회비 차액 | −5,000 |
| 접수 시각 | 10/8 14:00 |
| 근거 | 원문 메시지 또는 비고 |
| 처리 | 자동 반영 / 승인 대기 / 확인 요청 |

이 열 구성은 개발 시작 전에 둘이 먼저 확정합니다. 변동 반영 기능은 이 로그를 쓰고, 정산·리포트 기능은 이 로그를 읽습니다.

### 기술 구성

| 기능 | 구현 |
|---|---|
| 참가 입력, 본인 행만 수정 | Google Sheets + 행별 범위 보호 |
| 마감 잠금·스냅샷 | Apps Script 시간 기반 트리거 |
| 독촉·변동 접수 | Slack 봇 (Slack Bolt): 행사 채널 공지, 개인 DM |
| 입금 문자·캡처 인식 | LLM API (텍스트·이미지 입력) |
| 이름·메시지 해석 | LLM API |
| 계산·대조 | 스크립트 코드 |
| Slack 봇 서버 배포 | Render 등 |
| 개발·관리 | Cursor, GitHub, draw.io |

Slack 메시지를 받으려면 봇 서버가 필요해 배포가 들어갑니다. 일정이 빠듯하면 발송만 먼저 구현하고, 변동 접수는 시트 비고로 대체합니다.

## 3. AI 에이전트 구성: 기록·정산·소통

에이전트의 목표는 **"총무가 리포트만 보고 바로 송금할 수 있는 상태를 만든다"** 입니다. 세 에이전트가 역할을 나누고, 결과는 모두 변동 로그와 정산 현황 탭에 기록합니다.

| 에이전트 | 맡는 일 | 입력 | 출력 |
|---|---|---|---|
| 기록 Agent | 마감 후 변동 메시지, 입금 문자·캡처 해석 | Slack 메시지, 비고, 문자·캡처 | 변동 로그, 입금 내역 |
| 정산 Agent | 입금 대조, 회비 차액 계산, 리포트 | 입금 내역, 명단, 규칙 | 정산 현황, 정산 리포트 |
| 소통 Agent | 단계적 독촉, 환불 계좌 확인 | 정산 현황의 미납·환불 대상 | Slack 공지·DM, 총무 이관 목록 |

### 정산 Agent: 입금 대조 (핵심)

통장 입금 내역을 명단과 매칭하고, 금액을 최종 회비와 비교합니다.

| 입금자명 | 금액 | 에이전트 판단 |
|---|---|---|
| 이준호 | 20,000 | 명단과 일치 → 자동 납부 처리 |
| 민지김 | 15,000 | 이름 순서 변형 → 김민지로 매칭 |
| 영업2팀박서연 | 20,000 | 소속 표기 → 박서연으로 매칭 |
| 이준호(부) | 20,000 | 대리 입금 의심 → 확인 필요 |
| 김민지 | 20,000 | 동명이인 2명 → 확인 필요 |
| 박서연 | 15,000 | 같은 사람 두 번째 입금 → 이중 입금 의심 |

정확히 일치하는 매칭은 코드가, 이름 변형·소속 표기 해석은 LLM이 맡습니다.

### 기록 Agent: 마감 후 변동·입금 문자 반영

"저 버스 안 탈게요", "내일 못 갑니다" 같은 Slack 메시지나 비고를 읽고 변동 로그 한 줄로 구조화합니다. 은행 입금 알림 문자를 붙여넣거나 캡처를 올리면 입금자명·금액·시각을 추출해 입금 내역에 추가합니다. 거래내역 파일 업로드도 같은 형식으로 받습니다.

### 소통 Agent: 단계적 독촉·환불 확인

미납자, 추가 납부 대상자, 환불 계좌 미회신자에게 같은 단계 구조로 연락합니다.

| 단계 | 시점 | 방식 | 내용 |
|---|---|---|---|
| 1 | 마감 D-3 | 행사 채널 단체 공지 | 미입력·미입금 인원 수만 안내 (이름 없이) |
| 2 | 마감 D-1 | 개인 DM | 이름, 금액, 사유, 입금 계좌를 정중하게 안내 |
| 3 | 마감 당일 | 개인 DM | 마감 시각과 이후 처리 규칙을 사실 중심으로 안내 |
| 4 | 마감 후 미응답 | 총무에게 이관 | 자동 독촉 중단, 리포트의 '직접 연락 필요'에 표시 |

- 입금이 확인되거나 답이 오면 남은 단계는 즉시 취소합니다. 이미 낸 사람에게 독촉이 가지 않게 하는 것이 가장 중요합니다.
- 메시지에 [Q-012] 같은 요청 코드를 넣어 답장이 어떤 요청에 대한 것인지 정확히 연결합니다.
- 독촉 문구의 톤과 간격은 총무가 규칙 탭에서 조정합니다.

### 사람이 개입하는 지점 (HITL)

| 상황 | 에이전트 | 총무 |
|---|---|---|
| 이름·금액이 명확히 일치 | 자동 반영 | 리포트에서 확인만 |
| 이름 변형이지만 후보가 한 명 | 자동 매칭 + 표시 | 필요 시 확인 |
| 동명이인, 대리 입금, 이중 입금, 금액 불일치 | 반영하지 않고 확인 필요로 분류 | 결정 |
| "아마 못 갈 것 같아요" 같은 불확실한 표현 | 본인에게 확인 요청 발송 | 없음 |

## 4. 최종 산출물: 총무 정산 리포트

총무는 맨 위 결론과 확인 필요 항목만 보고 결정합니다. 나머지는 근거를 찾아볼 때 쓰는 부분입니다.

### 1. 결론

회비 총액 960,000원 / 수납 완료 945,000원. 확인 필요 2건 (동명이인 입금 1건, 이중 입금 의심 1건).

### 2. 확인 필요 (목표 0~3건)

| 항목 | 내용 | 선택지 |
|---|---|---|
| 동명이인 입금 | 김민지 20,000원, 명단에 김민지 2명 | 영업1팀 / 개발팀 |
| 이중 입금 의심 | 박서연 20,000 + 15,000 | 15,000 환불 / 다른 사람 대리 입금 확인 |

### 3. 송금 목록

| 구분 | 대상 | 금액 | 사유 | 상태 |
|---|---|---|---|---|
| 환불 | 3명 | 각 5,000 | 버스 → 자차 | 계좌 확인 2명 완료, 1명 대기 |
| 추가 납부 | 2명 | 5,000 / 20,000 | 자차 → 버스, 신규 참가 | 1명 완료, 1명 독촉 중 |

직접 연락 필요: 4단계까지 응답하지 않아 소통 Agent가 총무에게 넘긴 사람 목록입니다. 목표는 0명입니다.

### 4. 근거

마감 후 변동 로그, 입금 매칭 내역, 발송한 요청 기록 (링크로 연결)

## 5. AI 적용 전/후 워크플로

AI 적용 후 총무의 일은 "전체 명단 대조"에서 "예외 몇 건 결정"으로 줄어듭니다.

| 단계 | AI 적용 전 | AI 적용 후 |
|---|---|---|
| 신청 수집 | 메신저로 받아 표에 옮겨 적음 | 참가자가 시트 본인 행을 직접 수정 |
| 마감 | 마감 시점 명단을 수동으로 정리 | 자동 잠금 + 스냅샷 |
| 마감 후 변동 | 메신저 내용을 찾아 표에 반영 | 에이전트가 메시지를 해석해 로그·현황 갱신 |
| 입금 확인 | 통장 내역과 명단을 한 줄씩 대조 | 자동 매칭, 애매한 것만 확인 필요로 분류 |
| 미납·추가 납부 | 대상자를 찾아 개별 연락 | 소통 Agent가 단계적 독촉, 입금 확인 시 즉시 중단 |
| 환불 | 대상자 찾고 계좌 묻기 | 대상·금액·계좌가 정리된 송금 목록 |
| 총무가 보는 것 | 전체 표 | 리포트 1장, 확인 필요 0~3건 |

발표에서는 두 흐름을 flowchart(draw.io)로 나란히 그리고, 사람이 하는 단계에 색을 칠해 줄어든 정도를 보여줍니다.

- [ ] As-Is flowchart 작성
- [ ] To-Be flowchart 작성 (HITL 지점 표시)
- [ ] 시연 데이터로 측정한 수치 기입: 대조 대상 행 수 → 사람이 본 행 수

## 6. 시연과 검증

가상 데이터에 정답을 아는 문제를 심어두고, 에이전트가 몇 건을 찾는지 숫자로 보여줍니다.

가상 데이터: 참가자 50명, 입금 내역 약 55건, 마감 후 변동 메시지 7건

### 심어둘 문제 (약 10건)

| 유형 | 건수 | 기대 처리 |
|---|---|---|
| 이름 순서 변형, 소속 표기 | 3 | 자동 매칭 |
| 동명이인 | 1 | 확인 필요 |
| 대리 입금 | 1 | 확인 필요 |
| 이중 입금 | 1 | 확인 필요 |
| 금액 불일치 (15,000 대신 20,000) | 1 | 환불 대상 |
| 마감 후 버스 변경 메시지 | 2 | 변동 로그 + 차액 |
| 불확실한 표현 ("아마 못 갈 듯") | 1 | 본인 확인 요청 |

### 발표 지표

- 탐지: 심어둔 10건 중 몇 건을 찾았는가, 오탐은 몇 건인가
- 수고 감소: 대조 대상 55행 중 사람이 본 행은 몇 개인가

### 시연 흐름 (5분 내외)

1. 마감 전: 참가자가 시트에서 버스 칸 수정
2. 마감: 열 잠금, 스냅샷 생성
3. 마감 후: "저 버스 안 탈게요" 메시지 → 변동 로그와 차액 갱신
4. 입금 내역 업로드 → 자동 매칭, 확인 필요 분류
5. 미납자 단계적 독촉(Slack DM) → 입금 문자 붙여넣기 → 남은 독촉 자동 취소, 환불 계좌 요청 → 답장 반영
6. 총무 리포트 확인 → 결정 2건 → 송금 목록 완성

완성하지 못한 기능이 있으면 "왜 안 됐는지"도 그대로 공유합니다(강사님 권고).

## 7. 역할 분담과 일정

두 파트의 접점은 변동 로그와 정산 현황 탭의 열 구성 하나입니다. 이것만 먼저 합의하면 병렬로 개발할 수 있습니다.

| 박채원 | 김도형 |
|---|---|
| 정산 Agent: 입금 대조, 회비 차액, 정산 리포트 | 소통 Agent: Slack 봇, 단계적 독촉, 환불 계좌 확인, 답장 반영 |
| 시트 구조, 행 보호, 마감 잠금·스냅샷 | Slack 봇 서버 배포 |
| 발표: 문제 정의, 전/후 워크플로, 리포트 | 발표: 에이전트 구조, 시연 |

공통으로 할 일은 기록 Agent(변동 메시지·입금 문자 해석), 규칙 탭 확정, 가상 데이터 제작, 통합 테스트입니다.

## 9. 팀원 의견 반영 내역

팀원 제안 중 4가지는 이번 범위에 반영하고, 3가지는 발표 마지막의 '다음 단계'로 소개합니다.

| 제안 | 처리 | 이유 |
|---|---|---|
| 단계적 독촉 | 반영 (4단계, 입금 시 즉시 중단) | 미납·환불 연락 수고를 가장 크게 줄임 |
