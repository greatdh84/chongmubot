# 대모임(LARGE) 발표 시연 — 5~7분

모든 데이터는 가상입니다(300명·25팀, 이메일 `example.com`). 아래 수치는 **실측이라고 적힌 것만** 실제로 잰 값입니다.

## 0. 준비 (발표 10분 전)

```bash
# 저장소 루트. 처음 한 번: python3.11 -m venv .venv && .venv/bin/pip install -r hub/requirements.txt
(cd large/frontend && npm ci && npm run build)
(cd large/backend && ../../.venv/bin/python -m app.seed --reset)      # 시연 데이터 초기화(오늘 기준 날짜)
.venv/bin/python -m hub                                              # http://127.0.0.1:8787
```

- **초기화는 시연용 DB 에만 됩니다.** 시드가 만든 DB 에는 `db_meta.purpose='demo-seed'` 표시가 있고, 이 표시가 없는 DB(운영 데이터일 수 있음)나 `APP_MODE=production` 에서는 `--reset` 이 거부됩니다. 대상 파일: `large/backend/var/chongmu.db`.
- 같은 날짜 조건으로 똑같이 만들려면 `--base-date 2026-10-15` 처럼 기준일을 고정합니다(같은 시드·기준일 → 같은 사람·같은 거래).
- 실제 Gemini 로 시연하려면 `large/backend/.env` 에 `LLM_MODE=gemini`, `GEMINI_API_KEY=…` (Git 제외 파일). 키가 없거나 호출이 실패하면 규칙 기반으로 대체되고 **말풍선에 "⚠ LLM 실패 → 규칙 기반 대체"** 가 뜹니다. 화면 위 띠의 `LLM Gemini / LLM 모의(규칙)` 로 현재 모드를 확인하세요.
- 발표 등장인물(시드 고정, 초기화 출력에도 나옴): **T10 참가자**(주 장면), T10 담당자, T16·T19 담당자(입금자 불명), T13 담당자(중복 입금). `/large/` 첫 화면 '발표 등장인물' 버튼으로 바로 들어갈 수 있습니다.
- 백업: 브라우저 탭을 미리 열어 둡니다 — ① 총무(PC) ② 참가자(휴대폰 크기 창, 개발용 수신함의 초대 링크로 진입).

### 보조 사례
**A. 입금자 불명 'ㅎㅂ' 210,000원** — 확인 과제 탭 또는 T16 담당자 화면
- 정산 처리(규칙 R4)는 금액이 같은 미납 팀(T16·T19 등)을 **참고 후보로만** 기록하고 각 담당자에게 "우리 팀 입금인가요?"를 묻습니다. 금액이 같다는 이유로 배정하지 않습니다.
- 한 팀만 '네'면 배정 *제안*, 모두 '아니요'나 여러 팀 '네'면 총무 이관. → 사람: 담당자 답변·총무 확정 / 코드: 후보 계산·재검토. **LLM 은 이 판단에 쓰이지 않습니다.**

**B. 개인·팀 중복 입금(T13)** — T13 담당자 화면
- 장현우님 개인 20,000원 + 팀 일괄 입금 → 수납이 회비보다 20,000원 많음 → "팀 입금에 포함됐나요?" 확인 과제. '네' → 중복 납부로 정산 잔액에 추가 환불로 남음.

**C. 분할 입금(T22)** — 입금 대조 탭: 'T22 1차'·'T22 2차' 두 거래가 같은 팀으로 각각 제안됨.

### 마무리 멘트용 정리
- **LLM 이 하는 일**: 참가자·담당자 말 해석, 어떤 기록을 볼지(도구) 선택, 정보가 모자라면 질문, 변경 도구 선택.
- **코드가 하는 일**: 금액·환불 규칙 계산, 본인/자기 팀 권한, '네/아니요' 판정과 실제 기록, 중복 배정 방지, 입금 대조·확인 과제(규칙 R1~R6).
- **사람이 하는 일(HITL)**: 마감 후 변경 승인, 배정 확정, 이관 과제 처리, 정산 확정, 송금 결과 기록.

## 2. 실측 기록

### 실제 Gemini 검증 (2026-10-12, 합성 데이터·임시 DB, `scripts/llm_live_check.py`)
모델: `gemini-flash-latest` 우선, 한도·오류 시 `gemini-flash-lite-latest`. 판단 주체는 실행 기록의 `decisions[].by` 값.

| 단계 | 사용자 말 | 모델이 고른 행동 | 코드 실행 결과 | 걸린 시간 |
|---|---|---|---|---|
| ①② | "제 참석 응답이랑 회비가 지금 어떻게 되어 있어요?" | `get_my_status` → 답변 | 조회 성공, "참석+버스, 20,000원" | 5.4초 |
| ③ | "저 이번에 버스는 못 탈 것 같아요" | `ask`: 자차인지 불참인지 질문 | 상태 awaiting_info, 기록 변경 없음 | 5.0초 |
| ④⑤ | "제 차로 따로 갈게요" | `request_change{choice:car}` | 검증만 실행 → 확인 질문(입금 마감 후 버스→자차 환불 없음) | 4.3초 |
| ⑥⑦ | "네" | (코드 판정) | 변경 요청 기록 `pending_approval` + 총무 승인 과제 | 0.0초 |
| 권한 | "최지우님 응답을 불참으로 바꿔 주세요" | `preview_change{target:최지우}` → 거절 안내 | `FORBIDDEN`, 최지우 응답 그대로 | 7.6초 |
| 확인 모호 | "회사 일정 때문에 못 가요" → "음… 잘 모르겠어요 아마도요?" | 불참 확인 질문 → 두 번째 말에는 실행 없이 되물음 | 기록 변경 없음 | 6.5초 / 1.5초 |
| 담당자 | "네 맞아요"(과제 2개 열림) | `ask`: 어느 과제인지 질문 | 두 과제 모두 open 유지 | 14.7초 |
| 담당자 | "#2 번은 포함된 거 맞아요" → "네" | `answer_task{task_id:2, option:yes}` | #2 만 답변·해결, #3 open | 1.4초 / 0.0초 |

브라우저 리허설(공용 서버, Gemini 모드)에서도 장면 3~6 이 같은 결과로 진행됐습니다.

### 정산 처리(규칙 기반) — `scripts/demo_metrics.py` 1회 실행 (기준일 2026-10-15)
- 거래 28건 중 25건 배정 제안(high 22, medium 3), 나머지 3건(ㅎㅂ·김민준·결산이자)은 제안 없이 확인 과제·총무 이관
- 시드에 일부러 넣은 이상 사례 7개 중 7개가 의도대로 처리됨(입금자 불명, 동명이인, 이자, 중복, 개인 직접 입금, 메모 없는 담당자 입금, 분할 입금)
- 정산 처리 1회 0.03초(이 PC)

이 숫자는 **우리가 설계한 합성 데이터**에 대한 결과입니다. 실제 은행 거래내역에서의 자동 처리율·탐지율은 측정하지 않았습니다. 총무의 업무 시간 단축도 측정하지 않았습니다(워크플로 문서의 시간은 추정).

## 3. 문제가 생기면
| 증상 | 조치 |
|---|---|
| Gemini 응답이 느림·429 | 말풍선에 대체 표시가 뜨고 규칙 기반으로 계속 진행됨. 필요하면 `.env` 에서 `LLM_MODE=mock` 후 서버 재시작 |
| `/large/` 가 "화면이 아직 빌드되지 않았습니다" | `cd large/frontend && npm run build` |
| 데이터가 꼬임 | 서버 끄고 `app.seed --reset` 후 다시 실행 |
| 이메일이 안 보임 | 이메일 탭의 스케줄러 상태(15~60초 간격) 확인 또는 "지금 발송 실행" |
