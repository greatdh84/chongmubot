# PRD — 총무 Agent: 독촉부터 정산까지

## 1. 문제
300명·25개 팀 워크숍에서 총무는 참석 응답을 모으고, 마감 후 변경(버스→자차, 불참 등)을 반영하고, 팀별 입금과 개인 직접 입금을 은행 거래내역과 하나씩 맞춰 정산해야 합니다. 지금은 엑셀·메신저·전화로 처리해 다음이 반복됩니다.
- 미응답자·미납 팀을 손으로 골라 독촉
- 입금자명이 불명확하거나(“ㅎㅂ”), 동명이인이거나, 개인·팀이 이중으로 낸 입금을 일일이 문의
- 변경 시점에 따라 환불이 달라지는데 기준이 흩어져 있어 실수·분쟁 발생

## 2. 사용자 (Get Them)
| 사용자 | 한 문장 | 할 일(최대 2개) |
|---|---|---|
| 총무 | 행사 회비를 책임지는 관리 계정 | Agent 가 올린 확인 항목 승인, 정산 확정 |
| 참가자 | 링크 하나로 응답하는 직원 | 참석 방식 선택, 변경 요청 |
| 팀 담당자 | 총무가 지정한 팀 대표 | 팀 명세 확인, Agent 질문에 답변 |

## 3. 범위
### 포함 (이번 단계: 공통 뼈대)
- 실행 가능한 프런트(React+TS)·백엔드(FastAPI+SQLite), 외부 키 없이 동작
- 공통 데이터 모델과 API 계약 (`docs/api-contract.md`)
- 총무·참가자·담당자 기본 화면, 초대 링크 검증, 역할별 접근 제한
- 모의 Slack DM 수신함, 모의/Claude/Gemini LLM 어댑터, 소통·정산 Agent
- 재현 가능한 가상 300명·25팀 데이터 + 시나리오(변경, 입금자 불명, 동명이인, 개인·팀 중복 입금 가능성, 분할 입금, 미납, 담당자 미지정, 반송 메일)
- 금액 계산·권한·중복 배정 방지 테스트

### 제외
이메일, Slack 답장 자동 수집, 은행 API, 실제 송금, 배포, 팀 내부 수금 관리(회사 총무에게 납부된 회비만 관리).

## 4. 핵심 규칙
| 규칙 | 구현 위치 |
|---|---|
| 시연 회비: 버스 20,000 / 자차 15,000 / 불참 0 (행사별 설정) | `Event.fee_*` |
| 참석 마감과 팀 입금 마감 분리 | `Event.attend_deadline`, `payment_deadline` |
| 전체 명단 CSV(ID·이름·전화번호·Slack ID·소속 부서·팀 담당자) → 부서 = 팀, 담당자 자동 지정, 오류 시 전체 반려 | `services/roster.py` |
| 연락은 Slack DM: 인원조사는 개인, 회비·환불·추가 납부는 부서 담당자에게만 | `adapters/email.py`(Slack), `services/emails.py` |
| 납부 마감 청구표를 한 번 저장(수정 금지), 이후 변동과 비교해 보고서 | `TeamBilling`, `services/report.py` |
| 보고서는 버전으로 저장, 내용이 같으면 새 버전 없음, 이전 버전과 차이 기록 | `SettlementReport` |
| 마감 기준 응답은 한 번 저장 후 보존, 이후 변경은 이력으로 추가 | `DeadlineSnapshot`, `ChangeLog` |
| 마감 후 변경은 총무 승인 후 반영 | `ChangeLog.status=pending_approval` + `change_approval` 과제 |
| 변경 시점·항목별 환불 규칙. 감액분 × 환불률만 환불, 규칙 없으면 0원(총무 확인) | `RefundRule`, `services/fees.py` |
| 불참·버스 취소를 무조건 환불로 연결하지 않음 | 위 규칙 + 승인 단계 |
| 증액 변경: 부담액 = max(이전 부담액, 새 회비) | `fees.evaluate_post_deadline_change` |
| 미응답·미정은 회비 미확정, 자동 불참 처리 금지, 정산 확정 차단 | `fee_for → None`, 정산 blockers |
| 개인 직접 입금도 소속 팀 수납액에 포함, 팀 총 회비는 유지 | `Allocation.participant_id` |
| 입금 배정 합계 ≤ 거래 금액, 같은 거래·대상 중복 배정 금지 | `payments.allocate` + 부분 유니크 인덱스 |
| 정산 잔액 = 최종 회비 − 확정 수납액 + 이미 지급한 환불액 (양수 추가 납부, 음수 추가 환불) | `fees.settlement_balance` |
| 금액이 같다는 이유만으로 팀·원인을 확정하지 않음 | 정산 Agent R4: 후보 팀에 질문만 |
| 정산에는 총무가 확정한 배정만 반영 | `Allocation.status=confirmed` |

## 5. Agent 정의

총무 Agent(추가): 총무 질문 → 보고서 조회 도구 선택 → 답변. 갱신은 담당자 안내 발송 하나뿐이며 총무 '네' 후 코드가 실행. LLM 은 해석만, 숫자는 보고서.

| | 소통 Agent | 정산 Agent |
|---|---|---|
| role | 참가자·담당자의 창구 | 입금·응답 대조 담당 |
| goal | 요청을 정확한 기록으로 바꾼다 | 근거 있는 정산안을 만든다 |
| 흐름 | 요청 해석 → 본인·팀 권한 확인 → 기록 조회 → 부족한 정보 질문 → 사용자 확인 → 변경 기록 | 불일치 발견 → 기록 조회 → 확인 과제 생성 → 답변 재검토 → 배정 제안 또는 총무 이관 |
| LLM 역할 | 다음 행동 선택(도구/질문/답변) | 없음(규칙 R1~R6 코드) — 질문 문구 템플릿 |
| 코드가 하는 일 | 금액 계산, 접근 통제, 확인 판정, 실행 | 금액 계산, 중복 방지, 배정 합계 검사 |
| 기록 | `AgentRun`(근거 메시지·도구 호출·규칙·결과), 채팅 메시지 meta | `AgentRun`, `ConfirmTask.evidence/rule` |
